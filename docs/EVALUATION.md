# MacFish 方案评估与改进建议

> 评估对象：MacFish 的**方法论与技术方案本身**（不是代码细节——那些在
> [OPTIMIZATION.md](./OPTIMIZATION.md) 里）。
>
> 评估方式：以 README 的宣传为基准，逐条核对代码实现，再判断方案的方法论基础是否成立。
> 所有结论都附了可复核的证据（文件:行号）。

---

## 一、总体结论

**MacFish 的工程完成度是高的，但作为"预测引擎"的方法论基础不成立；作为"结构化推演沙盘"是成立的。**

问题的核心不在工程质量，而在于：**它输出的东西无法被验证，也没打算被验证。**
一个不声称可验证的创意工具没问题；一个声称"助决策在百战模拟后胜出"的预测引擎，
缺少校准环节就是根本性的。

### 宣传 vs 实现的对照

| README 的说法 | 代码里的实际情况 | 判定 |
|---|---|---|
| "透过**上帝视角动态注入变量**，精准推演未来走向" | 运行时可对模拟做的只有三件事：**采访单个/批量 Agent、关闭环境**（`simulation_ipc.py:25-29` 的 `CommandType` 只有 `interview` / `batch_interview` / `close_env`）。没有任何运行时注入事件的通道。"上帝视角"只出现在报告生成的 prompt 文案里（`report_agent.py:553,604,644`），是**措辞而非能力** | ❌ 未实现 |
| "自动解析预测需求 & **动态更新时序记忆**" | 行动回写图谱是真的（`ZepGraphMemoryUpdater`），这部分属实 | ✅ 成立 |
| "**GraphRAG** 构建" | 检索是 SQL `LIKE` 关键词匹配 + LLM 重排（`local_graph_store.py:329-339`），**全项目没有任何 embedding/向量能力**。这是 GraphRAG 最弱的一环 | ⚠️ 名不符实 |
| "最多**百万级 Agent** 模拟" | 每个 Agent 每轮一次 LLM 调用。100 万 Agent × 10 轮 = 10⁷ 次调用，在当前任何 LLM 价格下都不可行。代码里也**没有任何 Agent 数量上限或预算护栏** | ❌ 不可达 |
| "低成本，**常规模拟平均 5$/次**" | 与 Agent 数 × 轮数强相关，缺少用量的估算与显示 | ⚠️ 无量化依据 |
| "你的预测报告" | 报告是单条叙事，**没有置信度、没有情景分支、不标注不确定性**（`report_agent.py` 中 confidence / scenario / 概率 相关词零命中） | ❌ 缺关键输出 |

## 二、方法论评估：核心假设链条逐环拆解

MacFish 的隐含推理链是：

```
种子材料真实
  → LLM 抽出的图谱忠实于材料
  → 图谱实体能代表真实世界的行动主体
  → LLM 生成的人设能代表这些主体的真实行为倾向
  → Agent 在模拟社交平台上的互动能复现真实群体的互动
  → 因此模拟结果可外推到现实
  → 因此报告可指导现实决策
```

逐环判定：

| 环节 | 判定 | 说明 |
|---|---|---|
| ① 材料→图谱 | **有条件成立** | 截断到 3000 字符/批（`deepseek_graph_extractor.py:199`），chunk 仅 500 字，长文档的实体召回会明显损失 |
| ② 图谱→行动主体 | **有条件成立** | 本体被硬编码为**恰好 10 个实体类型**，且最后两个强制是 `Person`/`Organization` 兜底。对"电动车价格战"这类问题，真正的驱动主体是产能、库存、毛利——硬塞进"人/组织"两类会系统性扭曲模型 |
| ③ 人设→真实行为 | **不成立（最大风险点）** | 人设完全由 LLM 生成（`_generate_profile_with_llm`），本质是**模型对某类人的刻板印象**。同一实体类型的多个 Agent 共享同一套先验 → 模拟开始前就已经同质化，"回声室"是预置的，不是涌现的 |
| ④ 互动→真实群体 | **不成立** | 模拟只发生在 Twitter/Reddit。**只建模了"话语"通道，没有建模资源/结构通道**——价格、产能、供应链这些决定长期结果的东西没有 Agent 表征。所以系统天然高估"声量"、低估"结构" |
| ⑤ 外推 | **不可验证** | **全项目没有任何回测/校准/ground truth 机制**（backtest / 校准 / ground_truth 关键词零命中）。没有任何手段判断哪次预测对了 |
| ⑥ 指导决策 | **无依据** | 输出是单条确定性的叙事，无分布、无置信区间、无"什么情况下这个结论会错" |

### 一句话概括问题

**当前的输出是"LLM 认为会发生什么"的多轮角色扮演，而不是对现实的可校准预测。**
多 Agent 层增加了结果的方差和细节丰富度，但没有增加有效性——它把 LLM 的先验
重新包装成了一次"涌现"演示。

这不意味着项目没有价值。它在**创意推演**（推演小说结局）、**情景头脑风暴**、
**舆情演化机制探索**上是成立的，这些场景本来就不需要预测效度。需要调整的是定位与
对外表述，以及在需要效度的场景下补齐方法论的缺环。

## 三、具体缺陷清单（附证据）

### 3.1 已生成但从未被消费的配置——事件机制半接线

`SimulationConfigGenerator` 花了一整次 LLM 调用产出 `event_config`，其中包含
`initial_posts`、`scheduled_events`、`hot_topics`、`narrative_direction`（`simulation_config_generator.py:113-126`）。

但模拟脚本**只消费了 `initial_posts`**（`run_parallel_simulation.py:1172-1182`，
开局发帖）。`scheduled_events`（预排事件）、`hot_topics`（热点话题）、
`narrative_direction`（叙事走向）**在整个 scripts 目录里零引用**——生成完就扔掉。

这意味着：
- 白花一次 LLM 调用的钱
- 三者恰恰是"在时间轴上注入变量"的实现载体，**"上帝视角注入变量"其实只差最后一步接线**

### 3.2 图谱检索是关键词匹配

`search_nodes` / `search_edges` 是 `name/summary/labels` 上的 SQL `LIKE`
（`local_graph_store.py:329-339`），`DeepSeekGraphExtractor.semantic_search` 的做法是
"关键词粗筛（`limit*3`）+ LLM 重排"。全项目无 embedding。

后果：图谱一大（我们已经看到线上警告"Node count reached limit (2000)"），
关键词召回率急剧下降，且每次查询都要一次 LLM 重排调用——**又贵又差**。

### 3.3 没有可复现性

一次推演的完整参数（模型、温度、随机种子、人设采样、配置）没有被记录成 manifest。
两次相同输入会得到不同结果，且**无法审计"这份报告是怎么来的"**。
对一个要被拿去做决策的东西，这是硬伤。

### 3.4 没有成本护栏

Agent 数 = 图谱中带自定义标签的实体数，**没有上限**（`filter_defined_entities`
不做截断）。一份大材料可能抽出上千实体，直接变成上千 Agent × N 轮 LLM 调用，
没有预算预估、没有确认、没有中途熔断。

### 3.5 无断点续跑

`resume` / `checkpoint` 零命中。模拟跑到第 7 轮崩溃就要从第 0 轮重来
（`oasis.make()` 会删掉旧 db）。长模拟（几十分钟）里这是很痛的。

### 3.6 没有 LLM 调用缓存

同一份材料重复构建图谱，所有抽取调用全部重跑。开发/调试阶段这条尤其浪费。

## 四、改进措施（按投入产出比排序）

每条给出：**解决什么 / 怎么改 / 工作量 / 验收标准**。

### A 组：方法论补强（最高优先级，不做这些，其它优化都是在错误方向上跑）

#### A1. 回测框架 ⭐ 最高 ROI

- **解决**：方案不可证伪——这是当前最根本的缺陷
- **怎么改**：
  1. 建一个 `benchmarks/` 目录，每个 case 是一份"截止某日期的种子材料 + 该日期之后的真实结果"
  2. 加 `POST /api/benchmark/run`：跑完整管线，把报告和 ground truth 一起交给一个
     独立的评审 LLM，按固定 rubric 打分（关键主体是否命中 / 方向是否正确 / 关键事件是否提到）
  3. 产出记分卡：命中率、方向准确率、与真实值的秩相关
  4. **关键：种子材料必须在时间上严格早于结果**，否则是数据泄漏
- **工作量**：中（一个 case 的脚手架 + 打分 rubric；管线本身可直接复用）
- **验收标准**：20 个历史舆情事件上跑出方向命中率。**先接受它可能只有 50-60%**
  ——知道真实水平远好于不知道。有了这个基线，后面每一项优化都能被验证是否真的有效

> 这条是分水岭：没有它，团队无法判断任何改动是进步还是退步。

#### A2. 多次运行 + 稳定性输出 ⭐

- **解决**：点估计冒充预测；单次运行无法区分信号与噪声
- **怎么改**：同一输入跑 N 次（3~5 次），做两级聚合：
  - **图谱层**：实体/关系在不同运行中的复现率 → 稳定的实体是可信的骨架
  - **报告层**：把 N 份报告的结论做聚类，分成"稳定结论"与"摇摆结论"两类，
    报告里显式分组呈现
- **工作量**：小（纯编排 + 聚合，管线不用改）
- **验收标准**：报告中出现「稳定结论 / 摇摆结论」两组，且摇摆组能标出是哪些参数导致的

#### A3. 敏感性分析

- **解决**：不知道结论对哪些输入敏感
- **怎么改**：对关键参数（Agent 数、轮数、开局帖子、温度）做单变量扰动，
  记录结论是否翻转。翻转的结论一律降级标注
- **工作量**：小（复用 A2 的编排）
- **验收标准**：报告附一节「本结论对 X 敏感、对 Y 不敏感」

### B 组：保真度提升（决定模拟有没有"料"）

#### B1. 接完事件注入——把"上帝视角"真正实现

- **解决**：3.1 的半接线；README 的核心卖点目前是空的
- **怎么改**：
  1. 让脚本真正消费 `scheduled_events`（在指定轮次注入 `ManualAction` 发帖）
     和 `hot_topics`（作为该轮 Agent 可选动作的种子）——**这一步就把"按时间轴注入变量"落地了**
  2. 在现有文件 IPC 上加第四个命令 `inject_event`（`{round, content, poster_type}`），
     前端做一个"注入"入口 → 这是 README 所描述能力的**最小可用版本**
- **工作量**：小到中（IPC 加一个命令 + 脚本侧消费逻辑；IPC 框架已经现成）
- **验收标准**：模拟跑到中途注入一条事件，能在 `actions.jsonl` 与最终报告里看到它的影响

#### B2. 人设"接地"——用材料里的话，而不是模型编的话

- **解决**：环节③——人设是 LLM 刻板印象，同质化预置
- **怎么改**：抽取图谱时，把原文中该实体的**直接引语、表态、数字**一并存进节点属性；
  生成人设时以这些真实片段作为核心（而不是让 LLM 凭空编一份 bio）。
  种子材料里本来就有的原话，比生成的人格描述可信得多
- **工作量**：中（改抽取 prompt 的 schema + 人设 prompt）
- **验收标准**：随机抽 10 个 Agent，其 profile 里能追溯到原文出处的比例

#### B3. 强制异构性

- **解决**：同类型 Agent 同质 → 回声室预置
- **怎么改**：生成人设时显式要求覆盖对立立场，并把 `stance` 分布做成可配置
  （例如按 6:3:1 生成支持/反对/中立），而不是让 LLM 自由发挥
- **工作量**：小（prompt + 一点采样逻辑）
- **验收标准**：模拟结果中正/负/中立立场的分布符合配置，而非一边倒

#### B4. 结构化 Agent（混合仿真）——让长期因素也能被建模

- **解决**：环节④——只建模话语，不建模资源与结构
- **怎么改**：引入第二类 Agent：持有**数量状态**（产能、库存、现金、价格），
  按规则/公式行动（降价、扩产、退出），与 LLM 社会 Agent 双向交互
  （价格变化影响舆论，舆论影响销量）。这是"多智能体仿真"的成熟做法，
  比纯 LLM 聊天强得多
- **工作量**：大（需要领域建模）
- **验收标准**：在价格战类问题上，模型能给出价格走势，而不只是舆论走势

#### B5. 外部数据接入

- **解决**：只用种子材料，信息封闭
- **怎么改**：加一个可选检索阶段，把最新价格/新闻/公告作为补充输入并**标注来源**
- **工作量**：中
- **验收标准**：报告中的事实性陈述可追溯到具体的外部来源链接

### C 组：成本与规模

#### C1. 分层 Agent 架构 ⭐

- **解决**：3.4 的成本屏障；"百万级 Agent"不成立的根因
- **怎么改**：
  - **领航层（1~5%）**：LLM Agent，作为意见领袖，产生有质量的观点
  - **跟随层（95~99%）**：规则/统计 Agent，依据聚合信号（领袖观点分布、
    话题热度）按概率行动，单次成本接近零
  - 让 Agent 数量级从 10³ 提升到 10⁵ 成为可能，且**不牺牲话语质量**
- **工作量**：中到大（要改模拟脚本的 agent graph 与动作循环）
- **验收标准**：同等预算下模拟规模提升 ≥ 10 倍，且领航层观点质量不下降

#### C2. 向量检索替换关键词检索

- **解决**：3.2 检索质量与成本
- **怎么改**：给节点/边建 embedding（本地模型或 API），检索改为向量召回 + 图谱邻居扩展；
  LLM 重排从"每次必调"降级为"仅对 top-K 做精排"
- **工作量**：中
- **验收标准**：检索召回率提升，且单次报告生成的 LLM 调用次数下降

#### C3. 模型分层 + 调用缓存

- **解决**：用最贵的模型干最机械的活；重复调用不缓存
- **怎么改**：本体生成/图谱抽取/参数配置走便宜模型（这些是结构化抽取任务），
  模拟与报告用强模型；对确定性请求加内容哈希缓存（调试期收益最大）
- **工作量**：小
- **验收标准**：单次推演成本下降，且回测分数（A1）不下降

#### C4. 成本护栏

- **解决**：3.4 无上限
- **怎么改**：估算 Agent 数 × 轮数，前端在开始前显示**预估调用次数与费用**并要求确认；
  运行中超出预算自动暂停
- **工作量**：小
- **验收标准**：界面上能看到预估费用，且不会出现无意的天价运行

### D 组：可复现与工程

| 措施 | 解决 | 工作量 |
|---|---|---|
| **D1. Run Manifest**：每次推演记录模型版本、温度、种子、人设采样、配置哈希，随报告一起落盘 | 3.3 不可复现 | 小 |
| **D2. 每轮 checkpoint**：模拟按轮持久化状态，崩溃后可续跑 | 3.5 | 中 |
| **D3. 任务状态持久化**：`TaskManager` 落盘（见 OPTIMIZATION.md 1.5） | 重启丢任务 | 小到中 |

### E 组：输出的产品化 ⭐（性价比很高）

#### E1. 情景树代替单条叙事

- **解决**：报告是确定性叙事，决策者无法据此权衡
- **怎么改**：改报告大纲的 prompt——从"章节"改为"3~5 个命名情景 + 各情景的
  触发条件 + 相对可能性"。**决策者要的不是"会发生什么"，而是"什么情况下会发生什么、我怎么提前知道"**
- **工作量**：小（主要改 prompt 与大纲 schema）
- **验收标准**：报告包含情景树，每个情景带触发条件

#### E2. 先行指标

- **解决**：一次性报告用完即弃，无法持续跟踪
- **怎么改**：从模拟里反向提取"早期出现、且与结局相关的信号"
  （例如"第 2 轮开始出现渠道商抱怨"→ 现实中该关注什么）
- **工作量**：中
- **验收标准**：报告给出 3~5 个可观测的先行指标

#### E3. 断言级溯源

- **解决**：报告结论无法验证来源
- **怎么改**：现在报告已要求引用 Agent 原话（`report_agent.py:649-655`），这是
  **模拟内**溯源；再补上**材料内**溯源——每条事实性断言标注来自哪份种子文档/哪个图谱节点
- **工作量**：中
- **验收标准**：报告中的事实陈述可点回原始材料

## 五、建议路线图

> **实施进度（2026-10-06）**：第一期五项已全部实施，外加 B1 事件注入。
> - A1 回测框架 → `backend/app/services/benchmark*.py` + `scripts/run_benchmark.py`
> - A2 多次运行稳定性 → 同一 CLI 的 `--repeats N`，输出稳定/摇摆结论分组
> - D1 Run Manifest → `backend/app/services/run_manifest.py`
> - E1 情景树 → `ReportOutline.scenarios` + 报告装配 + 前端卡片
> - C4 成本护栏 → `backend/app/services/cost_estimator.py` + 预算上限
> - B1 事件注入 → `scheduled_events` 真正接通 + `inject_event` IPC（运行中可注入）
>
> 仍未做的：第二期的 B2 人设接地、B3 强制立场异构、E2 先行指标、E3 断言级溯源；
> 第三期全部（分层 Agent、向量检索、结构化 Agent）。
>
> **下一步最有价值的动作仍然是 A1 的「真实案卷」**：框架已就绪，但仓库里只有两个
> 明确标注为合成的演示案卷。往里面录入 20 个真实历史事件，才会第一次得到
> 「我们大约有多准」的答案——那才是这个项目从演示走向工具的分界点。

### 第一期：让方案"可被验证"（最高价值，建议优先投入）

| 项 | 内容 |
|---|---|
| A1 | 回测框架 + 20 个历史 case 的记分卡 |
| A2 | 多次运行 + 稳定/摇摆结论分组 |
| D1 | Run Manifest（可复现） |
| E1 | 情景树输出 |
| C4 | 成本预估与护栏 |

**交付后的状态**：项目第一次有了"我们的预测准确率大约是多少"的答案，
以及一个能持续度量改进的基线。**在此之前不建议再加任何新功能。**

## 六、不建议做的事

1. **不要在回测框架之前继续加功能。** 没有度量，新功能无法判断是进步还是退步，
   而且会在未经验证的方案上越走越远。这是当前最大的风险。
2. **不要为了"百万级 Agent"去硬堆数量。** 纯 LLM Agent 的路线撞的是成本墙，
   不是工程墙。正确路径是 C1 的分层架构，而不是优化并发。
3. **不要把报告写得更长更华丽。** 决策者需要的是置信度与情景，不是篇幅。
   当前报告已经很长，缺的是"这个结论有多可信"。
4. **不要接受"预测万物"的定位去做通用平台。** 选 1~2 个垂直场景做深并回测，
   比做一个什么都能沾一点的通用引擎有价值得多。通用性是结果，不是目标。
5. **不要为了让演示好看而调 prompt。** 一旦开始为了单次演示效果调 prompt，
   回测分数就会失去意义。

## 七、值得肯定的部分

评估应当公允，这个项目有几处判断是对的：

- **用本地 SQLite 替代 Zep Cloud** —— 去掉了外部依赖与月度成本，是明智的工程决策
- **全流程自动化程度高** —— 从上传到报告全自动，5 步交互设计清晰，实时进度反馈到位
- **文件 IPC 采访机制** —— 让"模拟结束后还能采访 Agent"成为可能，设计得干净
- **增量报告生成** —— 从 agent-log 事件流拼装报告，用户能实时看到章节生成过程
- **双平台并行模拟** —— Twitter/Reddit 两种平台机制并存，比单平台更有说服力
- **本轮刚补上的多格式上传 + 本地 OCR** —— 把输入端的门槛降到了实用水平

**结论：工程能力不是短板，方法论验证是。** 把第一期的四件事做完，
这个项目就从"看起来很厉害的演示"变成"知道自己有多准的工具"。
